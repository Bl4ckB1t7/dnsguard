## 结论摘要

真实 DNSGuard API/Web 流程已在隔离环境完成：初始化 → 白名单导入为草稿 → API 发布白名单 → API 添加并发布 A 重定向 → 隔离管理员最后启用全局 DENY。白名单、多级子域名、A 重定向和未知域名拒绝均通过。

公网 DNSLog 未执行：当前环境没有管理员提供的、可授权读取日志的 DNSLog 域名或 API 凭据，因此没有注册第三方账户、使用共享收件箱或把公网结果伪报为通过。

隔离模拟上游结果显示：DO=0 的随机 A/AAAA/TXT 查询未观察到上游 QNAME；DO=1 的 A/TXT 查询观察到完整 QNAME 到达模拟上游。该结果保留为安全失败，说明客户端收到 NXDOMAIN 不能等同于阻断 DNS 数据外传。

## 实际执行命令

### 隔离 BIND 首次部署顺序

```bash
STAGED_FIRST_DEPLOYMENT=1 ./tests/bind-cluster/global-deny-acceptance/run-acceptance.sh
```

结果：退出码 `0`。白名单先发布并完成三节点同步，随后启用 global DENY；白名单、多级子域名、A 重定向、未知域名 `NXDOMAIN` 和 DO=0 模拟上游检查通过。

### 同步失败保护

```bash
STAGED_FIRST_DEPLOYMENT=1 \
STAGED_INJECT_SYNC_FAILURE=1 \
./tests/bind-cluster/global-deny-acceptance/run-acceptance.sh --keep
```

结果：退出码 `1`。脚本在白名单同步失败后停止，未执行 global DENY 激活；随后仅清理本次创建的隔离 Compose 项目。

### 真实 DNSGuard API/Web 流程

使用隔离 BIND Compose 项目和临时 DNSGuard Compose 项目完成：

1. 构建 `dnsguard-api:e2e`、`dnsguard-web:e2e`。
2. 通过 HTTPS Web 代理调用 `/api/setup/complete`，HTTP 200。
3. 检查导入规则为 `draft`，`published` 为空。
4. 通过 `/api/dns/rpz/publish` 发布白名单，任务 `succeeded`。
5. 通过 `/api/dns/rpz` 添加 A 重定向，再通过同一发布 API 发布，任务 `succeeded`。
6. 仅在上述发布和同步完成后，修改隔离 BIND 的 `response-policy` 加载 global DENY 并重建隔离容器。
7. 使用容器内 `dig` 检查 Primary 和两台 Secondary 的实际解析结果。

API 发布使用了 DNSGuard 的真实控制面，不以测试脚本直接调用 `nsupdate` 代替 API 发布。容器内查询用于规避本机 Docker 端口转发在本次环境中的不稳定，不改变 BIND 或 DNSGuard 的生产架构。

### 隔离模拟上游 / DO 位

全局 DENY 已启用且 `qname-wait-recurse no` 的隔离配置下，生成随机 nonce，分别执行 DO=0 的 A/AAAA/TXT 和 DO=1 的 A/TXT 查询，并检查模拟上游容器日志。DO=1 的完整 QNAME 确实出现在模拟上游日志中，因此不能给出“完全阻断外传”的结论。

## 公网 DNSLog 未执行的原因

没有发现管理员提供的授权 DNSLog 配置，故以下变量均未使用：

- `DNSLOG_BASE_DOMAIN`
- `DNSLOG_QUERY_LOG_API`
- `DNSLOG_API_TOKEN`

如需补做公网验证，至少需要管理员提供本人拥有或明确授权的 DNSLog 基域名，以及可读取查询记录的 API 地址和 Token（若平台需要）。测试应使用随机 nonce、仅使用模拟数据，并保留合理等待窗口。

## 安全边界与剩余风险

- 本报告的上游结论只适用于本次隔离 BIND 版本、配置和受控模拟上游。
- 客户端 `NXDOMAIN` 不等于查询名称没有到达上游。
- 本次 DO=1 隔离测试仍观察到完整 QNAME 外传，未通过修改生产 BIND 配置掩盖该风险。
- 本次没有连接、修改或重启生产 BIND，也没有使用生产 TSIG。
- 未创建 Tag、Release 或合并 PR。
